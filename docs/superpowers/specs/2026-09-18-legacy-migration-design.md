# Local legacy daemon migration

Owner requested migration of the old global `~/.ours` installation into the unified installer on 2026-09-18. Extend the existing approved installer design with `--migrate-from /absolute/config.json --compatible`; the wizard collects the same choice. Source config may select a custom state directory. Destination must be a separate empty managed root, or the exact recorded target of an interrupted migration.

Read-only preflight checks private canonical files, actual state location, an authoritative running source daemon and its complete identity list, and ownership of the old boot service. External PostgreSQL state and unsupported external MCP/credential paths are refused explicitly. This migrates the daemon state and embedded MCP configuration; it does not copy unrelated global application directories.

Build the new exact runtime before downtime. Save a private journal plus original configuration/service bytes. Disable the positively identified source boot service, stop through the owning CLI, acquire the SDK-compatible Unix-socket state-root lock, and copy the complete opaque state tree including SQLite sidecars, keys, history, contact book, bindings and session state. Keep the source unchanged. Publish privately staged state atomically with an import receipt. Rebind deployment configuration, initialize/retain HMAC authority, and issue new consumer credentials. The old bearer token is not promised to remain valid.

Start the new daemon, compare every name/kind/CID with the original list, and never create a replacement Human during migration. Only then start managed applications. Emit a prepared host client profile and use the normal selected-integration pipeline. Keep the original daemon config intact: CLI daemon config is not a client profile. Preflight verifies the user-owned npm CLI entry and PATH. Cutover atomically replaces that entry with a selected-installation launcher, retaining its original metadata. Verify the ordinary default `ours identity list` after publication; a repeated completed migration repairs routing if npm has reinstalled the known CLI. Native routing uses the selected local CLI; Docker routing executes inside the selected daemon container. Daemon lifecycle routes through installer service ownership, and source-selection overrides are refused. Old boot service remains retired; original state is a recovery copy and must not run alongside the migrated state.

Journal and receipt make partial setup retryable. Before activation a retry may reattempt source shutdown and finish copying. After any activation attempt the imported destination is authoritative: stop the destination on failure and repair forward on retry, never automatically restart a stale source E2E session state. Complete migration repeats verify retained identities without bootstrap. This is local same-host migration, not a portable identity export.

Validation: author fixture tests for CLI/wizard parity, source and target rejection, opaque copying and sidecars, source locking, initialization/build interruptions, identity mismatch, post-activation repair and completion retries. Run only GitHub CI per Owner instruction; independent review covers the added migration before reporting it ready.
